# Правила оформления рисунков, таблиц, листингов и приложений

## Общие правила

Каждый объект должен иметь:

- уникальный номер из `docs/reports/correlation.md`;
- точное название;
- ссылку на объект в тексте;
- пояснение после объекта, если из него нужно сделать вывод;
- запись в `correlation.md`.

Подписи оформлять так:

- `Рисунок 1 - Архитектура сервиса семантического поиска`
- `Таблица 1 - Сравнение подходов к поиску по базе знаний`
- `Листинг 1 - Конфигурация embedding-моделей в application.yml`
- `Приложение А - Полный текст SQL-схемы базы данных`

Дефис в подписи использовать обычный `-`.

## Рисунки

Агент не рисует изображение напрямую. Вместо этого он вставляет:

1. номер и подпись рисунка;
2. краткое описание того, что должно быть изображено;
3. `Prompt для рисунка`, пригодный для генерации изображения в другой модели;
4. текстовый вывод после рисунка.

Шаблон:

~~~markdown
На рисунке 1 представлена общая архитектура разработанного сервиса.

**Рисунок 1 - Архитектура сервиса семантического поиска**

Prompt для рисунка: Создать строгую техническую схему на русском языке...

Из рисунка 1 видно, что разработанный сервис является промежуточным слоем между XWiki, моделью построения embeddings и векторным хранилищем PostgreSQL/pgvector.
~~~

Требования к prompt:

- указать язык подписей: русский;
- указать стиль: академическая схема, белый фон, единая стилистика;
- перечислить все блоки;
- описать стрелки и направление потока данных;
- запретить декоративные элементы, 3D, абстрактные фоны;
- если это график, указать данные, оси и единицы измерения.

Рекомендуемые рисунки для этой ВКР:

- архитектура системы;
- pipeline индексации XWiki;
- pipeline выполнения поискового запроса;
- схема БД `pages/chunks/embeddings`;
- Docker-контур системы;
- диаграмма распределения рангов;
- сравнение качества XWiki Solr и семантического поиска.

## Таблицы

Таблицы использовать для сравнений, характеристик, требований и метрик.

Шаблон:

~~~markdown
В таблице 1 приведено сравнение подходов к поиску по базе знаний.

**Таблица 1 - Сравнение подходов к поиску по базе знаний**

| Подход | Преимущества | Ограничения | Применимость в проекте |
| --- | --- | --- | --- |
| Полнотекстовый поиск | Быстрый поиск по точным словам | Слабая устойчивость к переформулировкам | Используется как baseline |
| Семантический поиск | Учитывает смысловую близость | Требует embedding-модели и векторного индекса | Выбран как основной подход |

По данным таблицы 1 выбран семантический подход, поскольку он лучше соответствует задаче поиска по неполным и переформулированным запросам.
~~~

Правила:

- не делать таблицы шире 4-5 колонок без необходимости;
- не дублировать в таблице длинные абзацы;
- после таблицы писать аналитический вывод;
- если таблица содержит метрики, указать датасет, K и дату/источник результатов.

## Листинги кода

Листинги использовать только для ключевых фрагментов, которые помогают понять реализацию.

Шаблон:

~~~markdown
В листинге 1 показан фрагмент endpoint, отвечающего за выполнение поиска.

**Листинг 1 - REST endpoint семантического поиска**

```java
@GetMapping("/search")
public ResponseEntity<List<SearchResultDto>> search(
        @RequestParam String query,
        @RequestParam(defaultValue = "5") int limit) {
    List<DocumentEmbeddingDto> urls = xWikiService.search(query, limit);
    List<SearchResultDto> result = xWikiService.getLinkResults(urls);
    return ResponseEntity.ok(result);
}
```

Данный фрагмент показывает, что controller не содержит логику ранжирования, а делегирует поиск сервисному слою.
~~~

Правила:

- включать 10-40 строк кода, если возможно;
- перед листингом объяснить, зачем он нужен;
- после листинга объяснить ключевые строки;
- не вставлять секреты, пароли и реальные credentials;
- большие классы переносить в приложения;
- для SQL и YAML использовать соответствующий язык в fenced block: `sql`, `yaml`, `powershell`.

## Приложения

Приложения нужны для материалов, которые важны для воспроизводимости, но перегружают основной текст.

Примеры:

- `Приложение А - Конфигурация Docker Compose окружения`;
- `Приложение Б - SQL-схема таблиц pages, chunks и embeddings`;
- `Приложение В - Фрагмент отчета evaluation`;
- `Приложение Г - Полный список REST endpoint сервиса`.

Правила:

- приложение должно быть упомянуто в основном тексте;
- название приложения должно объяснять его содержание;
- если в приложении код, сохранить форматирование и язык блока;
- не помещать в приложения секреты и пароли.
