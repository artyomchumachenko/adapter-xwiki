# Бизнес-контекст и качество поиска

## Бизнес-задача

Проект демонстрирует улучшение поиска по базе знаний XWiki за счет семантических embeddings и pgvector. Пользователь не обязан помнить точные слова из статьи: система должна находить релевантные страницы по смыслу, включая неполные, переформулированные и близкие по контексту запросы.

Ценность для пользователя:

- быстрее находить нужную wiki-страницу;
- видеть релевантный фрагмент текста, а не только заголовок;
- получать основу для RAG-ответа через `/api/xwiki/search/answer`;
- сравнить качество с обычным XWiki/Solr на измеримых метриках.

## Базовые метрики

В Python evaluation используются:

- `Hit@K` - попала ли правильная страница в top-K;
- `positional_accuracy_at_k` - фактически MRR/позиционная точность: `1/rank`;
- `nDCG@K` - штрафует низкую позицию правильного результата;
- `linear_score_at_k` - дополнительная линейная оценка позиции;
- rank distribution - сколько правильных страниц на rank 1, 2, ..., miss.

## Зафиксированные результаты из `XWikiTools/testing/out`

- dataset: `.\eval_dataset.csv`;
- queries: 60, errors: 0;

- `positional_accuracy@5 = 0.4617`;
- `nDCG@5 = 0.4713`;
- miss: 30 из 60, то есть 50%.

- `positional_accuracy@10 = 0.8323`;

- miss: 18 из 300, то есть 6%.

Прогон с rerank:

## Вывод по качеству

На доступных отчетах семантический Java search существенно лучше стандартного XWiki Solr baseline:

- Hit@K вырос примерно с 50% до 94%;
- доля miss снизилась примерно с 50% до 6%;
- rank 1 на большем датасете держится около 76%.

Rerank-прогон в текущих сохраненных метриках не улучшил качество: Hit остался тем же, а rank 1/MRR/nDCG стали ниже. Перед включением rerank в основной pipeline нужно отдельно проверить:

- какие candidates отправляются в reranker;
- используется ли текст chunk или title+snippet;
- не теряется ли правильный кандидат до rerank;
- latency на CPU;
- корректность сравнения на одном и том же датасете/K.

## Что считать регрессией

Для текущей системы подозрительным считается:

- `Hit@10 < 0.90` на `eval_dataset_100_queries.csv`;
- `rank_1_rate_pct < 70%` без осознанного trade-off;
- рост `errors > 0` в evaluation;
- заметный рост miss после изменений нормализации/чанкинга;
- ухудшение относительно XWiki Solr не по одной метрике, а по нескольким сразу.

## Как обновлять метрики

После изменений в поиске:

1. Поднять XWiki, vector DB, Ollama.
2. Запустить Java-сервис.
3. Если менялись чанкинг, модели, нормализация или schema, переиндексировать через `/api/xwiki/processAll`.
4. Запустить `testing/evaluate_search.py` на фиксированном CSV.
5. При необходимости запустить `testing/evaluate_xwiki_solr.py` для baseline.
6. Обновить этот файл: дата, dataset, K, модели, метрики, краткий вывод.

Важно: файлы `eval_top5_summary.json` и `eval_top5_with_rerank_summary.json` сейчас называются как top5, но внутри содержат `k = 10`. При ссылках на результаты ориентироваться на поле `k` внутри JSON, а не на имя файла.
