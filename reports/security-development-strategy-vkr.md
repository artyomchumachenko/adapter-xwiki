# Стратегия безопасной разработки для проекта ВКР

## Резюме

Проект `XWiki Adapter` реализуется как Spring Boot микросервис для индексации контента XWiki, семантического поиска и генерации AI-ответов. Оставшийся срок реализации составляет 5 месяцев. Команда предполагается небольшой: один backend-разработчик, автор ВКР как архитектор/исполнитель, преподаватель или научный руководитель как внешний стейкхолдер для приёмки результатов.

Цель стратегии — обеспечить базовый, но устойчивый уровень безопасной разработки, при котором риски проекта уменьшаются за счёт формализованных правил, встроенных проверок и контролируемой дорожной карты внедрения AppSec-практик.

## Ключевые риски и целевое состояние

Наиболее значимыми рисками являются:

- утечка знаний из XWiki через поиск и AI-ответы;
- неавторизованный доступ к административным API;
- подмена или загрязнение индекса и AI-контекста;
- утечка секретов интеграции;
- отказ в обслуживании из-за тяжёлых операций индексации и AI-вызовов.

Текущий уровень зрелости можно оценить как начальный: отдельные практики качества уже есть, но безопасность пока не встроена системно в SDLC. Целевое состояние на конец ВКР — базовый зрелый контур, включающий формализованные требования, модель угроз, code review, SAST, secret detection, SCA, API security testing и базовый DAST.

## Приоритетные практики

В дорожную карту включены следующие инициативы:

1. `OAD1` — политика безопасной разработки.
2. `OAD3` — регламент безопасной разработки.
3. `AC2` — ролевая модель.
4. `SC2` — регламент безопасного кодирования.
5. `SPA2` — code review.
6. `SPA3` — SAST.
7. `SPA7` — детектирование секретов.
8. `SCA1` — компонентный анализ зависимостей.
9. `QA4` — тестирование API.
10. `DPA2` — базовый DAST на тестовом контуре.

Эти практики выбраны потому, что они прямо закрывают риски проекта и реалистичны для внедрения в течение 5 месяцев.

## Дорожная карта

### Квартал 1

- Формализовать политику и регламент безопасной разработки.
- Зафиксировать ролевую модель и правила безопасного кодирования.
- Обязать code review для всех изменений.
- Встроить SAST и secret detection в процесс разработки.

### Квартал 2

- Внедрить SCA для Maven-зависимостей.
- Усилить API testing негативными и security-сценариями.
- Запустить базовый DAST на тестовом окружении.
- Связать результаты проверок с критериями допуска изменений.

## Метрики успеха

- количество критичных дефектов, найденных до merge;
- среднее время исправления security-дефекта;
- количество найденных секретов до публикации изменений;
- доля зависимостей без High/Critical CVE;
- количество критичных находок DAST на тестовом стенде;
- доля изменений, проходящих security-проверки без ручного обхода.

## Роли и ответственность

- Автор ВКР / backend-разработчик: реализация технических практик, настройка SAST/SCA/DAST, правки кода.
- Архитектор проекта: актуализация модели угроз, security-требований и архитектурных ограничений.
- AppSec-функция в рамках учебного проекта: ведение дорожной карты, контроль статусов, анализ метрик.
- Научный руководитель / преподаватель: внешняя проверка артефактов и принятие результатов.

## Итог

Для проекта ВКР целесообразна стратегия «меньше практик, но глубже внедрение». Это позволит получить не формальный перечень инициатив, а работающий минимальный AppSec-контур, который реально снижает риски и улучшает качество итоговой системы.
