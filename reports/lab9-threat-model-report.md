## 3. Результаты Части 1. Анализ архитектуры и построение DFD

### 3.1. Краткое описание архитектуры проекта

Исследуемая система представляет собой Spring Boot 3 микросервис `XWiki Adapter`, который выполняет три основные функции:

1. Индексация контента из XWiki.
2. Семантический поиск по уже проиндексированным страницам.
3. Генерация ответа на основе найденного контекста с помощью LLM.

На основе анализа кода проекта были выявлены следующие компоненты.

| Категория | Компонент | Назначение | Протокол/порт | Зона доверия |
|---|---|---|---|---|
| Внешняя сущность | Пользователь | Выполняет поиск и задаёт вопросы | HTTP/HTTPS, `server.port` | Внешняя сеть |
| Внешняя сущность | Администратор/оператор | Запускает переиндексацию, отладочные AI-вызовы | HTTP/HTTPS, `server.port` | Внешняя сеть |
| Процесс | REST Controllers | Точки входа `/api/xwiki`, `/api/chat`, `/api/embedding` | HTTP/HTTPS | Контур приложения |
| Процесс | `XWikiService` | Оркестрация индексации и поиска | Внутрипроцессные вызовы | Контур приложения |
| Процесс | `PageProcessor` + `PageContentService` | Загрузка контента страниц, нормализация, чанкинг | Внутрипроцессные вызовы | Контур приложения |
| Процесс | `EmbeddingSearchService` | Генерация embeddings запроса и поиск похожих чанков | Внутрипроцессные вызовы | Контур приложения |
| Процесс | `XWikiClient` | Запросы к XWiki REST API | HTTP(S) REST + Basic Auth | Граница с внешней системой |
| Процесс | `LlamaAiClient` | Запросы к Ollama для chat и embeddings | HTTP REST | Граница с внешней системой |
| Хранилище | PostgreSQL + pgvector | Хранение страниц, чанков, embeddings | JDBC / PostgreSQL 5432 | Зона данных |
| Внешняя система | XWiki REST API | Источник страниц и контента базы знаний | HTTP(S) REST | Внешняя интеграция |
| Внешняя система | Ollama / AI service | Генерация embeddings и ответов LLM | HTTP REST | Внешняя интеграция |

### 3.2. Выявленные API и потоки данных

Из кода контроллеров и сервисов были определены ключевые API:

- `GET /api/xwiki/processAll` — запуск полной индексации пространств и страниц XWiki.
- `POST /api/xwiki/processPage?pageId=...` — принудительная обработка одной страницы.
- `GET /api/xwiki/search?query=...&limit=...` — семантический поиск по индексу.
- `GET /api/xwiki/search/answer?query=...` — генерация ответа на основе лучшего результата поиска.
- `GET /api/chat?message=...` — прямой вызов chat-модели.
- `GET /api/embedding?message=...` — прямой вызов модели embeddings.

Ключевые внутренние потоки:

1. Индексация:
   клиент -> контроллер -> `XWikiService` -> `XWikiClient` -> XWiki -> `PageContentService` -> `PageProcessor` -> `LlamaAiClient` -> PostgreSQL.
2. Поиск:
   клиент -> контроллер -> `XWikiService` -> `EmbeddingSearchService` -> `LlamaAiClient` -> PostgreSQL -> контроллер.
3. Генерация ответа:
   клиент -> контроллер -> поиск -> подбор контекста -> `LlamaAiClient` -> возврат ответа.

### 3.3. Границы доверия

В модели выделены три основные границы доверия:

1. Между внешними клиентами и микросервисом.
2. Между микросервисом и внешними интеграциями (`XWiki`, `Ollama`).
3. Между сервисным контуром и зоной данных (`PostgreSQL + pgvector`).

### 4.3. Топ-5 наиболее критичных угроз

1. `TM-01` — неавторизованный запуск административной индексации.  
   Обоснование: угроза напрямую затрагивает контур управления сервисом и может быть реализована удалённо при минимальных усилиях.

2. `TM-08` — утечка содержимого закрытых страниц через поиск.  
   Обоснование: компрометирует главный бизнес-актив проекта, а именно знания из XWiki и производные сниппеты.

3. `TM-10` — раскрытие чувствительного контента во внешний AI-сервис.  
   Обоснование: затрагивает конфиденциальность и compliance; риск особенно критичен для корпоративной базы знаний.

4. `TM-11` — DoS через многократный запуск `processAll`.  
   Обоснование: одна операция нагружает сразу XWiki, AI и БД, поэтому имеет высокий мультипликативный эффект.

5. `TM-03` — prompt injection через данные из XWiki.  
   Обоснование: характерный риск RAG-систем, ведущий к ложным ответам и возможной утечке контекста без взлома инфраструктуры.

## 5. Результаты Части 3. Требования безопасности

### 5.1. Итоговый список требований безопасности

#### Аутентификация и управление доступом

1. Все endpoint'ы `/api/xwiki/processAll`, `/api/xwiki/processPage`, `/api/chat`, `/api/embedding` должны быть доступны только аутентифицированным субъектам.
   Проверка: интеграционные тесты `401/403` для неавторизованных запросов.
   Покрывает: `TM-01`, `TM-02`, `TM-14`.

2. Для административных операций должна быть выделена роль `ADMIN_INDEXER`, а для пользовательского поиска отдельная роль `SEARCH_USER`.
   Проверка: тесты авторизации по ролям и матрица доступа.
   Покрывает: `TM-01`, `TM-14`.

3. Публичные и служебные API должны быть логически разделены: служебные endpoint'ы должны публиковаться только во внутреннем контуре или через отдельный gateway.
   Проверка: ревью маршрутов и сетевой конфигурации.
   Покрывает: `TM-02`, `TM-14`, `TM-15`.

#### Конфиденциальность и шифрование

4. Соединения с XWiki, AI-сервисом и пользовательскими клиентами должны использовать TLS; для внутренних сервисов рекомендуется mTLS.
   Проверка: конфигурация HTTPS, сертификаты, сетевые тесты.
   Покрывает: `TM-09`, `TM-10`.

5. Секреты `XWIKI_USERNAME`, `XWIKI_PASSWORD`, параметры БД и AI должны храниться в защищённом хранилище секретов, а не в открытых конфигурационных файлах.
   Проверка: аудит deployment-конфигурации и CI/CD.
   Покрывает: `TM-09`, `TM-15`.

6. Результаты поиска не должны возвращать `textSnippet` и URL страницы, если пользователь не имеет права чтения соответствующей страницы в XWiki.
   Проверка: интеграционные тесты с пользователями с разными ACL.
   Покрывает: `TM-08`.

7. Для страниц, содержащих чувствительные данные, должен поддерживаться режим запрета отправки текста во внешний AI-сервис.
   Проверка: тестовый сценарий с пространством, исключённым из AI-обработки.
   Покрывает: `TM-10`.

#### Целостность данных и логики

8. Контент, полученный из XWiki, перед использованием в RAG должен проходить нормализацию и защитную фильтрацию от prompt injection-маркеров и управляющих инструкций.
   Проверка: unit/integration tests на вредоносные payload'ы.
   Покрывает: `TM-03`, `TM-04`.

9. Операции изменения индекса должны сопровождаться контролем целостности и возможностью восстановления из резервной копии.
   Проверка: регламент backup/restore, тест восстановления.
   Покрывает: `TM-05`.

10. Для БД должны использоваться отдельные роли: чтение поиска, запись индексации, миграции схемы.
    Проверка: аудит ролей PostgreSQL и прав GRANT.
    Покрывает: `TM-05`, `TM-15`.

#### Аудит и неотказуемость

11. Каждая административная операция должна логироваться с указанием пользователя, времени, endpoint'а, параметров и результата выполнения.
    Проверка: наличие audit log и тестов логирования.
    Покрывает: `TM-06`, `TM-07`.

12. Для переиндексации должны сохраняться метаданные запуска: инициатор, число обработанных страниц, ошибки AI/XWiki и версия обработанных документов.
    Проверка: наличие таблицы/журнала запусков и отчётов.
    Покрывает: `TM-06`, `TM-07`.

#### Доступность и устойчивость к отказам

13. На endpoint'ах поиска, chat и embedding должны быть введены ограничения на размер входных данных, rate limiting и защита от burst-нагрузки.
    Проверка: нагрузочные тесты и negative tests.
    Покрывает: `TM-11`, `TM-12`.

14. Полная индексация должна запускаться только как одиночная фоновая задача с блокировкой параллельного старта и с очередью повторных запросов.
    Проверка: интеграционный тест на конкурентные вызовы.
    Покрывает: `TM-11`.

15. Для вызовов XWiki и AI должны использоваться таймауты, retry с backoff и circuit breaker, чтобы отказ внешней системы не приводил к каскадной деградации.
    Проверка: chaos/integration tests с искусственной недоступностью зависимостей.
    Покрывает: `TM-13`.

- `TMR1` — формализация требований безопасности на основании выявленных угроз.
- `TMR2` — построение и фиксация модели угроз для текущей архитектуры.
- `TMR3` — регулярная актуализация модели угроз при изменениях API, архитектуры и состава AI-моделей.

Кроме того, уточнены ближайшие технические задачи: внедрение аутентификации и авторизации, сегментация API, защита секретов, аудит, отказоустойчивость и защита от DoS.

## 7. Ответы на контрольные вопросы

### Что такое Threat Modeling и зачем оно нужно?

Threat Modeling — это систематический подход к выявлению и анализу потенциальных угроз безопасности на этапе проектирования архитектуры. Для проекта ВКР это позволяет заранее обнаружить слабые места в логике работы с XWiki, AI-моделями и БД до того, как они приведут к инцидентам в эксплуатации.

### Почему использована методология STRIDE?

STRIDE хорошо подходит для архитектурного анализа микросервисов и DFD-диаграмм, так как охватывает шесть ключевых классов угроз: подмена, модификация, отказ от авторства, раскрытие информации, отказ в обслуживании и повышение привилегий. Для `XWiki Adapter` этого достаточно, чтобы структурированно проанализировать REST API, внешние интеграции и БД.

### Почему для данного проекта особенно важны границы доверия?

Сервис работает на стыке сразу трёх доменов доверия: пользовательские клиенты, внешняя wiki-система и AI-сервис. Именно на этих стыках возникает наибольшее число угроз: неавторизованные вызовы, отравление данных, утечка контента и каскадные отказы.

## 8. Выводы

В процессе моделирования угроз выяснилось, что главные риски проекта лежат не только в инфраструктуре, но и в логике RAG-конвейера. Наиболее критичными оказались отсутствие встроенной аутентификации для административных endpoint'ов, потенциальная утечка внутренних знаний через поисковую выдачу и передача контента во внешний AI-сервис.

Полученные требования безопасности напрямую влияют на дальнейшую разработку: необходимо внедрить Spring Security, разграничение ролей, аудит, защиту от DoS, политику работы с чувствительными данными и регулярное обновление модели угроз. Практический вывод состоит в том, что даже локальный интеграционный микросервис без явной «боевой» экспозиции остаётся высокорисковым, если он соединяет внешние API, базу знаний и генеративные модели.
